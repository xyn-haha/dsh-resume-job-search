# 岗位匹配度评估（Job Evaluation Framework）

> 门控规则（Gate）：**先评估匹配度，得到用户确认后才写简历。**
> 在用户确认评估结论之前，不生成简历（CV）、不生成求职信（Cover Letter）。本文件只负责评估与结论。

---

## 1. 何时触发（When to Use）

- 用户给出职位信息：招聘平台职位页 URL（BOSS直聘、猎聘、智联招聘、前程无忧、拉勾等）、公司官网招聘页、校招/实习公告链接。
- 用户直接粘贴 JD（Job Description，职位描述）文本或截图文字。
- 用户提出："这个岗位适合我吗""值得投吗""帮我对比这几个 JD""这个实习怎么样"。
- 自动触发条件：任何准备写简历/求职信/面试准备的请求，若还没有针对该岗位的书面评估结论，先执行本技能。

不触发的情况：用户只是要修改简历排版、改写已有求职信，且已明确同一岗位评估已完成并确认。

---

## 2. 输入解析（URL 或粘贴 JD 文本）

1. **接受两种输入**：URL，或粘贴的 JD 文本。
2. **URL 处理**：先抓取页面正文（使用 `web_search` 能力检索 + 抓取页面正文），必要时读取用户本地保存的页面副本文件（如 `.html`/`.txt`/`.md`）。
   - 若目标站点有反爬（如 BOSS直聘、猎聘常需登录）：抓取失败时不要反复重试，直接请用户粘贴 JD 文本，或改用用户提供的截图文字。这类失败只记为事实，不影响后续评估流程。
3. **提取结构化字段（能提取多少就提取多少）**：

| 字段（Field） | 说明 |
|---------------|------|
| 岗位名称（Role Title） | 原文名称 + 职级线索（实习/校招/初级/社招） |
| 公司名称（Company） | 全称或品牌名，用于第 3 节核实 |
| 工作地点（Location） | 城市/园区，用于第 4 项地点判定 |
| 岗位职责（Responsibilities） | 逐条列出，用于技术技能与职业对齐打分 |
| 必备要求 vs 加分要求（Must-have / Nice-to-have） | 若 JD 未区分，明确标注"未区分"，并在电话沟通建议中列为问题 |
| 经验与学历要求（Experience / Education） | 年限、专业、学历门槛 |
| 薪资（Salary） | 区间或"面议" |
| 联系方式（Contact） | 是否有可联系的 HR/用人经理 |
| 投递方式与截止时间 | 邮箱/平台/内推；校招节点 |

4. **信息缺失处理**：缺失字段不要臆测；在评估表 Notes 中标注"JD 未说明"，并把"该信息缺失"转化为第 7 节电话沟通或投递前确认的问题。

## 3. 公司核实（Company Verification）

在打分前先做基本核实，避免对着空壳公司做深度评估。**核实结论只作为事实记录与打分依据，不得当成漏洞式"发现"夸大。**

使用 `web_search` 能力检索 + 抓取页面，优先以下渠道：

- **公司官网**：使命、价值观、主营业务、近期新闻与融资/上市动态。
- **企业信息平台**：天眼查、企查查（成立时间、注册资本、实缴、参保人数、司法风险、经营异常、股权结构）。
- **主流媒体与行业媒体**：裁员、业务调整、增长、合规处罚等报道。
- **招聘平台职位页**：BOSS直聘、猎聘上该公司在招岗位数量、同类岗位薪资公开区间、岗位是否长期挂出（长期挂出可能是人才储备而非真实需求）。
- **职场评价平台**：脉脉、看准网（适用于中国大陆主体）等，查看面试体验、管理风格、加班氛围。

**公司核实检查清单（Company Research Checklist）**

- [ ] 已查看公司官网（使命、价值观、近期新闻）
- [ ] 已查看企业信息与评价平台（天眼查/企查查；脉脉/看准网等）
- [ ] 已在招聘平台查看团队规模、近期在招岗位、同类岗位薪资公开区间
- [ ] 已查看媒体报道（重组、扩张、裁员、职场争议等）
- [ ] 已识别可能认识该团队/直属上级的人脉联系人

**薪资对比**：JD 未给薪资或薪资异常时，用**同级岗位在 BOSS直聘/猎聘的公开区间**做横向对比；无法获取公开区间时标注"待确认"，不要编造数值。

## 4. 匹配度评分表（Scoring Dimensions）

对每个岗位按以下维度打分。**评分规则、分档、权重与阈值必须按本节执行，不得删减。**

### 4.1 技术技能匹配（Technical Skills Match，0-100）

岗位要求/加分技能与候选人能力的吻合程度。

| 分数 | 含义 |
|------|------|
| 80-100 | 核心要求即候选人的主要技能（primary skills） |
| 60-79 | 大部分要求匹配，有 1-2 项可通过学习补齐的差距 |
| 40-59 | 部分匹配，需要显著补课（upskilling） |
| 0-39 | 根本性不匹配（fundamental mismatch） |

**分档方法**：按 `candidate-profile/SKILL.md` 的「技术技能」三档（熟练 / 使用过 / 了解）与「技术方向」逐项对照 JD 的硬性要求与加分项，得出三张清单：

- **强匹配**：`candidate-profile` 中标为「熟练」且 JD 要求明确的技术项（逐条列出技术名）。
- **中等匹配**：标为「使用过 / 了解」、或可迁移的邻近技术项。
- **弱匹配**：JD 要求但资料库中不存在的能力，以及岗位所在领域所需的深度经验（如某些平台类、合规类或特定工程实践），逐条列为差距。

清单里的每一项都必须能追溯到 `candidate-profile` 的具体条目，禁止凭岗位名称推测候选人具备某能力。

### 4.2 经验匹配（Experience Match，0-100）

工作履历与岗位期望的吻合程度。

| 分数 | 含义 |
|------|------|
| 80-100 | 同领域、同角色类型的直接经验 |
| 60-79 | 相关经验，可迁移技能清晰 |
| 40-59 | 邻近经验，需要自己论证可迁移性 |
| 0-39 | 无关经验 |

分档时以 `candidate-profile/SKILL.md`「实习与工作经历」「项目经历」为唯一依据：

- **强（Strong）**：与目标岗位同领域、同角色类型的项目或实习经历（逐条点名具体项目与承担的角色）。
- **中（Moderate）**：可迁移的邻近经历，例如课程实践、工具链开发、跨职能协作。
- **入门级定位（Entry-level）**：先判断求职身份（在读学生 / 应届生 / 社招）。在读或应届时，经验来源是项目与竞赛而非职业工作经历，目标岗位应锁定实习、校招、初级/入门岗位；社招时按实际工龄与职责范围评估，不得拔高。

### 4.3 行为/文化契合（Behavioral / Culture Fit，0-100）

岗位与公司文化是否匹配行为画像（细致可靠的执行者；在期望明确、技术有深度的结构化环境中表现出色）。

| 分数 | 含义 |
|------|------|
| 80-100 | 文化与行为偏好高度匹配 |
| 60-79 | 信号混合但总体兼容 |
| 40-59 | 存在一定摩擦点 |
| 0-39 | 明显的文化不匹配 |

**需重点调研的红旗（Red flags to research）**：团队混乱无组织、岗位职责定义模糊、放养式上手（sink-or-swim onboarding）、几乎没有带教（minimal mentorship）、优先级频繁变动。

### 4.4 地点与物流（Location & Logistics，通过/不通过 + 备注）

以 `candidate-profile/SKILL.md` 的「所在城市 / 是否接受异地 / 是否接受出差」为基准逐条判定：

| 情形 | 判定 |
|------|------|
| 位于首选城市或明确接受的城市 | PASS（理想） |
| 位于接受范围内但需通勤/搬迁成本 | PASS（需在备注中写明成本与是否可接受） |
| 全远程（境内） | 按用户是否接受远程判定 PASS / FLAG |
| 需搬到未接受的城市或海外 | FLAG（需与用户讨论后再决定是否投递） |
| 频繁出差或倒班 | FLAG（结合用户红线判定） |
| 违反用户登记的红线（工作制、行业等） | FAIL（不投递） |

地点为通过/不通过（pass/fail），**不参与加权**；判定结论必须写出触发该判定的具体资料条目。

### 4.5 职业对齐与动机（Career Alignment & Motivation，0-100）

岗位是否推进职业目标，且任务本身是否让人有动力。

| 分数 | 含义 |
|------|------|
| 80-100 | 与职业方向高度一致，成长路径清晰 |
| 60-79 | 岗位不错，但与长期目标仅部分对齐 |
| 40-59 | 岗位还行，但不指向职业目标的积累 |
| 0-39 | 死路或倒退一步 |

**职业目标（Career goals）**：从 `candidate-profile/SKILL.md` 的「求职偏好」中读取目标岗位关键词、目标行业与城市优先级，逐条对照本岗位是否推进这些目标，而不是套用固定方向。

**动机筛选（Motivation filter）**：不仅评估「能否做这些事」，还要评估「这些事是否会让人有动力」。从 `candidate-profile` 与 `behavioral-profile` 中提取：

- 让人有动力（energize）：资料库里「什么让人兴奋」「优势」对应的任务类型。
- 让人消耗（drain）：资料库里「需要成长的地方」「红线」对应的任务类型。
- 非任务因素：管理风格、部门文化、公司价值观、自主度。

**个人境况对齐（Life situation alignment）**：从资料库读取身份（在读 / 应届 / 社招）、可到岗时间、每周可投入时间、经济压力与优先级排序，判断该岗位在**时间与节奏**上是否可行；无法从资料库得出的，向用户提问而不是假设。

### 4.6 薪资基准（Salary Benchmark，可选扩展）

> 该维度为**可选扩展**，**不参与加权**，不因此扣分。默认做法是检索公开区间：用 DSH 联网搜索该岗位在 BOSS直聘 / 猎聘 / 看准网上的同级岗位薪资区间，取 2–3 个来源交叉比对。若用户自备结构化薪资数据文件，则改为查询本地数据。

结果呈现格式：

```
### 薪资基准（Salary Benchmark）
| 指标 | 数值 |
|------|------|
| 检索到的区间（来源 A） | X–Y / 月（YYYY-MM 抓取） |
| 检索到的区间（来源 B） | X–Y / 月（YYYY-MM 抓取） |
| 交叉结论 | 该岗位在 <城市> 的市场区间约为 X–Y |

```

解读纪律：

- 只给**区间参考**，不给确定承诺，不把某一家的数据当作事实。
- 必须标注抓取时间与来源渠道；样本过少（少于 2 个来源）时明确写「样本不足，仅供参考」。
- 若岗位薪资明显低于检索区间，视为红旗写入评估结论；明显偏高时提示核实真伪（是否外包、是否为绩效浮动口径）。

> 可选扩展（未被原始规则覆盖、仅在需要时补充，不参与加权）：行业景气度、岗位稳定性、通勤距离估算、落户/社保/公积金等本地政策适配。若使用这些扩展项，必须标注为「可选扩展」，且不得改变本文件定义的权重与阈值。

### 4.7 权重（Weighting）

- 技术技能（Technical Skills）：30%
- 经验匹配（Experience Match）：25%
- 行为契合（Behavioral Fit）：15%
- 职业对齐（Career Alignment）：30%

（地点与物流为通过/不通过，**不参与加权**。）

**总体评分 = 各计分维度的加权平均（Overall Score: XX/100，weighted average of scored dimensions）**。

### 4.8 阈值与判定（Thresholds）

| 判定（Verdict） | 区间 | 行动 |
|------|------|------|
| **强烈适合（Strong Fit）** | 75+ | 一定要投，全面定制材料 |
| **适合（Good Fit）** | 60-74 | 投递，在求职信中回应差距 |
| **中等（Moderate Fit）** | 45-59 | 谨慎考虑，与用户讨论 |
| **偏弱（Weak Fit）** | 30-44 | 除非有战略理由，否则大概率跳过 |
| **不适合（Poor Fit）** | <30 | 跳过 |

## 5. 风险与红旗（Risk & Red Flags）

汇总四类风险，每条给出"证据/来源"与"待确认项"，与事实区分开，**不得把猜测写成结论**：

1. **岗位与公司风险**：JD 职责与标题不符、必备/加分边界不清、岗位长期挂出、公司经营异常（天眼查/企查查司法风险、参保人数异常、经营异常名录）、频繁改架构或裁员报道。
2. **团队与管理风险**：见 4.3 红旗清单（团队混乱、职责模糊、放养式上手、缺带教、优先级频繁变动）。
3. **地点与物流风险**：需搬迁海外、频繁国际出差、通勤不可行。
4. **薪资与合规风险**：薪资区间与同级公开区间偏离过大、口头承诺不写进 offer、劳务/外包用工性质（注意区分正式编制与外包/派遣）。

---

## 6. 结论与行动建议（是否投递 / 是否需要先电话沟通）

### 6.1 投递建议

按 4.8 阈值给出：**投递（Apply）/ 带条件投递（Apply with caveats）/ 谨慎考虑并先与用户讨论 / 建议跳过**。结论必须写出 1-2 句理由。

### 6.2 投递前：给用人单位打电话（最佳实践，Pre-Application: Call the Employer）

在撰写申请材料之前，考虑候选人是否应致电 JD 中列出的联系人。**只在存在实质性问题时才打电话**——绝不要仅为了"被记住"而打。

**建议致电的情形（When to Suggest Calling）**：
- JD 中存在不清楚或含糊的要求
- 无法判断哪些能力是必备（essential），哪些是加分（nice-to-have）
- 岗位描述对日常工作内容语焉不详
- 有具名联系人且公开表示欢迎咨询

**适合提问的问题（Good Questions to Ask）**：
- "这个岗位最主要的工作挑战是什么？"
- "岗位职责中列出的各项，时间通常是如何分配的？"
- "哪些能力对这个岗位的成功最关键？"
- "入职前 6-12 个月，什么样的表现算成功？"

**通话规则（Rules for the Call）**：
- 准备 30 秒的"电梯陈述"（elevator pitch）介绍自身背景，以防对方问起
- 通话目的是**获取信息**，不是做自我推销
- 做好记录——用获得的信息来定制申请材料
- 在求职信中自然引用这次交流（例如："在与 [姓名] 交流后，我尤其被……吸引"）

```
[1-2 句：投递 / 跳过 / 带条件投递]

### 公司核实清单

- [ ] 已查看企业信息与评价平台（天眼查/企查查；脉脉/看准网等）
- [ ] 已在招聘平台查看团队规模、近期在招岗位、同类岗位薪资公开区间
- [ ] 已查看媒体报道（重组、扩张、职场争议等）
- [ ] 已识别可能认识该团队/直属上级的人脉联系人
```

### 输出纪律

- 打分必须给出分档依据；无法判断的维度标注"信息不足，估值"并说明依据，不虚构分数。
- 事实（可溯源）、推断（基于事实的分析）、假设（待确认）三者分开书写。
- **不得在任何输出中粘贴用户隐私数据**；候选人档案内容只作为方法示例引用，不整段复述个人联系方式、证件等信息。
- 评估结论输给用户后，**等待用户确认**；确认后才进入简历定制环节（见流水线中 `resume-writing/SKILL.md`）。
