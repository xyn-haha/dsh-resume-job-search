# 岗位情报搜集与去重台账（job-search-intel）

用一个可复跑的流程，把「找岗位 → 确认职位 → 去重 → 打分 → 短名单 → 投递台账 → 技能补差」串成闭环。所有结论必须来自真实的搜索结果或抓取到的原始职位页，**绝不编造职位、薪资或要求**。

---

## 一、自然语言触发（不再使用斜杠命令）

本技能通过自然语言动作触发，同类意思的说法都算命中：

| 动作 | 用户可能的说法 | 技能行为 |
|---|---|---|
| 找新岗位 | 「找新岗位」「搜一下安全岗」「有没有新职位」「看岗位」 | 执行第一~五节：检索 → 抓取确认 → 去重 → 适配速评 → 呈现 |
| 批量排序 | 「批量排序」「给这些岗位打个分」「按匹配度排一下」「做个短名单」 | 执行第六节：批量打分 → 短名单 |
| 评估这个 JD | 「评估这个 JD」「分析这个岗位」「这个职位值不值得投」 | 先做完整适配评估（技能/经验/文化三层），再决定是否生成短名单条目 |
| 更新台账 | 「我投了 XX」「记录一下投递」「更新台账」「有回音了」 | 执行第八节：写台账行 + 同步状态 |
| 技能差距 | 「我缺什么」「技能差距」「该学什么」「学习计划」 | 执行第九节：差距分析 → 学习计划 |

可带限定词：
- **聚焦方向**：「找新岗位 安全工程」「搜岗位 蓝队」→ 只跑对应优先级的检索式，并额外生成 2–3 条该方向的自定义检索式。
- **放宽范围**：「大范围搜」「广搜」→ 跑全部优先级类别（默认只跑前 3 类）。

## 二、渠道与检索策略

### 2.1 渠道清单（中国求职市场）

**主渠道**

| 渠道 | 定位 | 检索入口 |
|---|---|---|
| BOSS直聘（zhipin.com） | 直接与招聘方沟通，技术岗覆盖强 | 站内搜索 + 城市筛选 |
| 猎聘（liepin.com） | 中高端岗位，偶有实习 | 站内搜索 |
| 智联招聘（zhaopin.com） | 综合类岗位体量最大 | 站内搜索 / 站内 `site:` 检索 |
| 前程无忧（51job.com） | 全国性综合招聘 | 站内搜索 / 站内 `site:` 检索 |
| 拉勾（lagou.com） | 互联网／技术岗集中 | 站内搜索 |
| 实习僧（shixiseng.com） | 实习与校招实习岗 | 站内搜索 |
| 牛客网（nowcoder.com） | 校招内推、笔试面经、岗位帖 | 讨论区与校招板块 |

**补充渠道**

- **公司官网招聘页**：校招页（campus.xxx.com）、社招页、招聘公众号推文。对已知目标公司优先用 `site:` 检索直达招聘页。
- **公众号**：招聘信息常以推文发布，做关键词检索后抓取正文。
- **GitHub / 安全社区招聘帖**：如各类 `hiring`、`jobs` 仓库、`招聘` label 的 issue、安全社区招聘板块。适合安全／小众方向。

### 2.2 检索机制优先级

1. **首选：本插件自带的本地检索 CLI（`lib/jobfetch.mjs`）**。它在可用渠道上返回结构化字段（岗位名、城市、薪资、时长、毕业年份、截止时间、链接），并自带去重状态机，是最省 token、最不打扰平台的路径。用法（在插件仓库目录下执行，`--state` 指向求职工作区，避免把岗位记录写进仓库）：

   ```bash
   node lib/jobfetch.mjs search --city 南京 --limit 12 \
     --keywords 安全,渗透测试,安全服务,网络安全 \
     --state <工作区>/job_scraper/seen_jobs.json
   ```

   参数含义：`--city` 多城市用逗号分隔（留空不限城市）；`--keywords` 逐个作为检索词跑列表页并合并去重；`--limit` 本次新增上限；`--json` 输出机器可读结果；`--state` 去重状态文件（与 `seen_jobs.json` 同结构）。

   调用纪律：先读 `lib/JOBFETCH.md` 的渠道能力矩阵，**只对标记为「可匿名检索」的渠道使用**；同一命令行复跑会自动跳过已见过的岗位；非零退出时记录错误并降级到第 2 条，不要重试轰炸。

   已知限制（2026-10 实测）：牛客网列表接口**不按关键词过滤**，结果会混入非目标岗位，需要粗筛或人工判断；详情接口目前拿不到公司名；BOSS直聘/猎聘/智联/前程无忧/实习僧 在登录墙后，**命令行走不通，必须请用户人工浏览并把 JD 文本贴回来**。
2. **其次：DSH 联网搜索 + 网页抓取**。没有可用渠道、CLI 不可用或失败时，用 DSH 的联网搜索能力执行第 2.3 节检索式，再对命中 URL 做网页抓取（高校就业网、公司官网招聘页通常可匿名抓取）。这是大多数国内渠道的常态路径。

无论走哪条路径，都要记录每个结果的**来源渠道**，后续台账 `Channel` 列要用；CLI 返回的线索同样要按第 2 步抓原始职位页确认关键要求后才能采信。

### 2.3 检索式（按优先级分类）

每条检索式都要与**地域词**组合使用。地域词不是写死的，从 `candidate-profile/SKILL.md` 的「所在城市 / 期望工作城市 / 城市优先级」中取，下文示例用 `{CITY}`、`{PROVINCE}`、`{REGION}` 占位；用户所在地或接受城市变化时只改资料库，不改本节。括号内为渠道适配提示。

写法统一为：`岗位关键词 + 地域词 + 可选限定词（实习/校招/内推）`。

**优先级 1：与资料库「目标岗位关键词」第一优先方向对应的核心岗位**

```
（BOSS直聘）<核心岗位词> {CITY} OR {PROVINCE}
（智联招聘）"<核心岗位词英文或全称>" {PROVINCE}
（前程无忧）"<核心岗位词>" {CITY} OR {PROVINCE}
（智联招聘）"<同义岗位词>" {PROVINCE}
（猎聘）"<核心岗位词>" {CITY}
（牛客网）<方向关键词> 校招 内推 {PROVINCE}
site:zhaopin.com "<核心岗位词>" {CITY} OR {PROVINCE}
site:51job.com "<核心岗位词>" {CITY} OR {PROVINCE}
```

**优先级 2：相邻方向岗位（同一技能栈的第二落点）**

```
（智联招聘）"<相邻岗位词 A>" {CITY} OR {PROVINCE}
（前程无忧）"<相邻岗位词 B>" {CITY} OR {PROVINCE}
（智联招聘）"<相邻岗位词 C>" {PROVINCE}
（BOSS直聘）"<相邻岗位词 A>" OR "<相邻岗位词 B>" {CITY}
site:zhaopin.com "<相邻岗位词 C>" {PROVINCE}
site:51job.com "<相关系统或平台词>" {CITY}
```

**优先级 3：新增长方向 / 前沿岗位（资料库「技术方向」里的进阶方向）**

```
（猎聘）"<前沿方向词>" OR "<同义前沿方向词>"
（智联招聘）"<前沿方向词>" OR "<同义前沿方向词>" 中国
（智联招聘）"<细分前沿方向>" OR "<另一细分方向>" {PROVINCE}
site:51job.com "<相关合规或治理方向>" {PROVINCE}
```

**优先级 4：泛方向 / 入门 / 实习（读「求职身份」决定是否启用）**

```
（实习僧）"<方向>实习" {CITY} OR {PROVINCE}
（智联招聘）"<方向>实习生" {CITY} OR {PROVINCE}
（BOSS直聘）"实习" "<方向>" {CITY}
（拉勾）<方向> 实习 {CITY}
site:51job.com "<方向>" 实习 {CITY}
```

**填充规则**：`{CITY}` / `{PROVINCE}` 从资料库地域字段取；`<核心岗位词>` 等占位符从资料库「目标岗位关键词」与「技术技能 / 技术方向」中取原词，一个占位符一条检索式，禁止凭空编造岗位词。目标是让检索式随资料库变化自动更新，而不是维护一份固定清单。

**自定义扩展**：用户给出聚焦方向时，从上述对应类别取检索式，再补 2–3 条该方向的长尾检索式；渠道不限于主渠道清单，公司官网、公众号、GitHub／安全社区招聘帖按关键词组合检索。

## 三、执行步骤

### 第 0 步：加载状态

1. 读 `job_scraper/seen_jobs.json`；文件不存在就用 `{"seen": {}}` 初始化。
2. 读 `job_search_tracker.csv`，抽出已投递／已跟进的 `Company + Role` 组合。
3. 读本技能文件中的检索策略（第 2.3 节）；若有独立的检索式清单文件，一并读取。

### 第 1 步：检索

- 默认跑**前 3 个优先级类别**；用户说「大范围／广搜」跑全部 4 类；用户给了聚焦方向就只跑对应类别 + 自定义检索式。
- 按第 2.2 节优先级选择机制（本地脚本 优先，否则联网搜索 + 抓取）。
- 时间窗：**近 14 天**内发布，或投递截止日期尚未过期。
- 单次调用控制结果数量（约 20 条以内），保持低频、低并发；命中量大时按渠道分批，而不是抬高频率。
- 把所有结果汇入一个候选池，每条都标注来源渠道。

### 第 2 步：抓取原始职位页并确认关键要求

**扫描器／搜索命中的岗位只是线索，必须抓取原始职位页确认关键要求后才可采信。**

对候选池里值得深入的结果，抓取其原始职位页（渠道详情页或官网招聘页），提取：

- 岗位标题、公司、工作地点、发布或截止日期
- **关键硬性要求**（学历／专业、年限、技能栈、证书）
- 岗位职责要点
- 一句话岗位描述

规则：
- 不要对每一条搜索命中的结果都抓取——先用标题与摘要预筛，只抓有潜力的。
- 抓取失败或页面失效：记录为「待确认」，不要凭摘要推断要求。
- 逐条过滤：
  - URL 已在 `seen_jobs.json` 中 → 跳过
  - `公司 + 岗位` 已在 `job_search_tracker.csv` 中 → 跳过
  - 岗位已过期、已关闭、或明确写明截止日期已过 → 跳过
  - 明显超出地理范围（需远距离搬迁且不在可接受列表）→ 跳过并登记原因

### 第 3 步：适配速评（快速信号，不是完整评估）

给每个通过过滤的岗位打一个粗粒度标签：

- **高匹配**：岗位直接用到核心技能（Web 漏洞评估、渗透测试方法论、流量分析、AI 安全、蓝队／应急响应等）
- **中匹配**：岗位与经验相邻（安全运营支撑、安全设备监控、合规与信息安全管理等）
- **低匹配**：岗位要求大量当前不具备的技能

这是**速评**，用于排序与预筛，不等同于第六节的完整打分。

### 第 4 步：去重与存储（`seen_jobs.json` 状态机）

把本轮所有抓取过的岗位（**包括被跳过的**）写入 `seen_jobs.json`，键为 URL 或 `公司_标题` 组合：

```json
{
  "seen": {
    "<url_or_company_title_key>": {
      "title": "...",
      "company": "...",
      "url": "...",
      "first_seen": "YYYY-MM-DD",
      "fit": "high/medium/low",
      "status": "new/skipped/evaluated/ranked/expired"
    }
  }
}
```

**status 取值语义（状态机）**

| status | 含义 | 何时写入 |
|---|---|---|
| `new` | 新捕获、尚未处理 | 首轮抓取入库 |
| `skipped` | 主动略过 | 过期／关闭／超范围／低匹配且不深入 |
| `evaluated` | 已完成单岗完整适配评估 | 用户点选「评估这个 JD」后 |
| `ranked` | 已进入批量打分排序 | 批量排序动作处理后 |
| `expired` | 已失效 | 后续复盘中确认截止或下架 |

`ranked` 与 `expired` 都视为「已见过」，去重时不再作为新岗位呈现。

**增量字段（只在批量排序时追加，绝不丢弃已有字段）**

- `rank_score`：0–100 总体分
- `rank_verdict`：匹配档位（如 `strong fit` / `possible fit` / `weak fit`）
- `rank_date`：打分日期（ISO 格式）

写入时把该条 `status` 置为 `ranked`；若条目已有其它字段（如 `fit`、`detail`），重写时原样保留。

### 第 5 步：呈现结果

按匹配度排序（高匹配在前）输出表格，并给出高匹配条目的要点：

```
## 新岗位匹配 — YYYY-MM-DD

本轮新增 X 个岗位（高 Y / 中 Z / 低 W）。

| # | 匹配度 | 岗位 | 公司 | 地点 | 截止 | 渠道 | 链接 |
|---|--------|------|------|------|------|------|------|
| 1 | 高 | ... | ... | ... | ... | BOSS直聘 | [链接](...) |

### 高匹配重点
每个高匹配岗位 2–3 条：
- 与本方向匹配的原因
- 需要核对的硬性要求（学历／证书／年限）
- 风险点（如要求经验超出当前水平、薪资口径模糊）
```

呈现后追问一句：「要不要深入评估其中某几个？给我编号即可。」

- 用户给出编号 → 走完整适配评估（技能匹配 / 经验匹配 / 文化匹配三层），评估结论良好再进入简历与求职信环节。
- 本轮新增岗位较多（约 8 个以上）→ 主动建议做**批量排序**：对全部新岗位按完整匹配框架打分并返回短名单，比逐条目测更可靠。

### 第 6 步：批量打分排序 → 短名单

1. 对每个 `status` 为 `new`（或用户指定范围）的岗位，按完整匹配框架打 0–100 分，给出档位结论。
2. 回写 `seen_jobs.json`：追加 `rank_score`、`rank_verdict`、`rank_date`，`status` 置为 `ranked`。
3. 输出短名单：按 `rank_score` 降序，只保留档位达到「可投」的条目，每条附一行理由 + 一条待确认信息。
4. 短名单中的岗位若无对应台账行，提示用户是否需要建档。

### 第 7 步：投递

用户决定投递某个岗位时：先做完整适配评估，评估通过再生成针对性简历与求职信；**薪资只做区间参考，不给确定承诺**，不要替用户承诺可接受的薪资数字。

### 第 8 步：更新台账

发生投递或状态变化时，把结果写进 `job_search_tracker.csv`：

- 新增行：`AppliedDate`、`Company`、`Role`、`Source`（原始职位页 URL）、`Channel`（渠道）、`Location`、`SalaryRange`、`Status`、`NextAction`、`ResumeFile`、`CoverLetterFile`、`Notes`
- 状态变化（笔试／面试／offer／拒绝／无回复）：只更新对应行的 `Status`、`NextAction`、`Notes`，不新开重复行
- 表头与示例行见同目录 `job_search_tracker.csv`；CSV 内不写注释行，字段说明见下：

| 列名 | 含义 |
|---|---|
| AppliedDate | 投递日期 YYYY-MM-DD |
| Company | 公司名 |
| Role | 岗位名 |
| Source | 原始职位页 URL |
| Channel | 渠道（如 BOSS直聘、猎聘、公司官网） |
| Location | 工作地点 |
| SalaryRange | 薪资区间（仅参考） |
| Status | 台账状态（见下） |
| NextAction | 下一步动作 |
| ResumeFile | 投递所用简历文件路径 |
| CoverLetterFile | 投递所用求职信文件路径 |
| Notes | 备注（联系人、笔试面经、反馈） |

台账 `Status` 常用取值（与 `seen_jobs.json` 的状态机区分，台账记录的是**投递后**的阶段）：
`to_apply`（待投递）、`applied`（已投递）、`screening`（筛选中）、`test`（笔试／作业）、`interviewing`（面试中）、`offer`、`rejected`、`no_response`、`withdrawn`。

### 第 9 步：自我复盘

每轮结束前检查：是否已投递岗位的 `NextAction` 到期、是否有已过期但仍被引用的岗位、是否出现重复行。发现重复行合并保留信息最完整的一行。

## 四、地理范围与时间窗

**地理优先级**（呈现与打分时都要考虑；具体城市从 `candidate-profile/SKILL.md` 的地域字段读取，下列为判定方法而非固定清单）

- **优先**：首选城市及通勤可达的同城圈（资料库「所在城市 / 期望工作城市」）
- **可接受**：资料库中列为可接受的城市与周边城市（考虑通勤或搬迁成本，写入备注）
- **可考虑**：岗位集中度高、机会明显更强时才考虑的城市（需与用户确认是否接受搬迁）
- **避免**：资料库红线中排除的地区；需签证支持的海外岗位；与资料库地点偏好冲突且无法远程的岗位

**时间窗**

- 只收录**近 14 天**内发布的岗位，或投递截止日期尚未过去的岗位。
- 只收录未过期、未关闭的岗位。
- 若无法确定发布日期，可以收录，但必须标注「发布日期未知」。

## 五、技能差距 → 学习计划

把已跟踪岗位与当前能力矩阵对比，找出差距并给出按优先级排序的学习计划。

### 5.1 两种模式

- **汇总模式**（用户说「我缺什么」「技能差距」而不给具体岗位）：分析台账中全部已跟踪岗位。
- **定向模式**（用户给出某个 JD 的 URL 或原文）：只分析这一个岗位。

### 5.2 加载数据

- 汇总模式：读台账全部行，记下每行的 `Role`、`Company` 与匹配评分（0–100，越低的岗位暴露的差距越多，权重越高）；读能力矩阵（技能、经验、证书、竞赛与项目）；若存在上一份报告（`gap-plans/report-YYYY-MM-DD.md`），加载用于差异对比。
- 定向模式：抓取该岗位原始页面，提取必需技能、加分技能、职责与领域背景；不读取台账。

### 5.3 第 1 遍：硬技能差分

1. 从每个岗位来源提取**必需技能**与**加分技能**。
2. 汇总模式：建立**技能频次表**（某技能被多少个岗位提到），并施加匹配权重：每个岗位的技能计数贡献乘以 `(100 - 匹配评分) / 100`，即匹配度越低的岗位对差距分贡献越大；某技能最终得分 = 各岗位 `权重 × 出现次数` 之和。
3. 定向模式：无权重，必需技能与加分技能等权；必需技能在前，组内按字典序。
4. 与能力矩阵对比，**移除**能力矩阵中已有的技能。判定要宽松——能力矩阵中以任何形式出现过的相关技能都算已具备，避免误报。
5. 剩下的就是**硬技能差距清单**：汇总模式按得分降序；定向模式必需差距在前、加分差距在后，组内字典序。

### 5.4 第 2 遍：整体综合（补充差分漏掉的差距）

换角度整体判断，并给每条差距打类型标签 `[domain]`／`[soft]`／`[tooling]`／`[credential]`：

- **领域知识差距**：对岗位所处行业或问题空间不熟悉（如 AI 安全、IoT 安全、数据安全合规）
- **软技能差距**：岗位强调的工作方式、沟通方式或协作期待尚未体现在能力矩阵中
- **工具与流程差距**：跨岗位反复出现但自身缺失的框架、平台或流程（如 MLOps、CI/CD、安全运营流程与工单体系）
- **证书／资质差距**：多个岗位把某证书列为必需或加分时标记

不要重复第 1 遍已收录的差距，只补漏项。定向模式下所有综合差距都源自同一岗位。

### 5.5 差距热力图（优先级排序）

合并两遍结果，输出一张带优先级的表（作为中间结论先展示，再看学习计划）：

| 优先级 | 技能 / 领域 | 类型 | 差距来源 |
|---|---|---|---|
| Critical | 应急响应实操 | Hard | 4/5 个岗位，得分 3.2 |
| High | AI 安全领域知识 | Domain | 综合判断 |
| High | CI/CD 与安全左移流程 | Tooling | 综合判断 |
| Medium | 云平台安全（进阶） | Hard | 2/5 个岗位，得分 1.1 |
| Low | ... | ... | ... |

优先级判定：

- **Critical**：高权重／高频硬技能，或出现在多数已跟踪岗位中的领域差距
- **High**：中等得分的硬技能，或稳定反复出现的软技能／工具流程差距
- **Medium**：低频硬技能，或仅在少数岗位出现的综合差距
- **Low**：一次性提及或无关紧要的加分项

定向模式按岗位自身措辞定级：必需技能 → Critical 或 High；加分技能 → Medium；推断出的差距 → Medium 或 Low。

### 5.6 学习计划

为每个 **Critical / High** 差距（若差距总数少于 5 个，Medium 也纳入）生成一条学习条目：

1. **联网检索**当前高评价的学习资源；检索式带上**当前年份**避免过期结果，例如「最适合入门的应急响应实操课程 2026」「某技能 面向安全岗的学习路线 2026」。
2. **挑选 2–3 个资源**，优先顺序：带动手实验的课程 > 官方文档（工具类差距）> 书籍（领域知识差距）。每个资源给出名称、链接、一句适配理由。
3. **结合自身基础写学习方向**，明确「跳过什么、从哪里开始」。例如已掌握流量分析基础，就说明跳过工具入门章节，直接从真实样本的协议级分析与告警研判入手。
4. **估算达到可上手水平的时间**（如 ~20h、~40h 打牢基础），宁可估多不估少。

**按主题分组**（不要按字母序堆列），推荐主题：安全基础与进阶、蓝队与安全运营、AI 安全、云与基础设施、工具与流程、领域知识、证书与资质。

条目格式：

```
### 蓝队与安全运营

**应急响应与主机取证** `[Hard]` — ~25h
- [资源 1](url) — 带实操靶场，适合先动手后补理论
- [资源 2](url) — 官方文档，动手后作为查阅手册

学习方向：已具备 Windows/Linux 基础操作与日志查看能力，跳过系统管理入门章节，
直接从事件时间线重建、持久化机制排查与内存取证工具链开始。
```

### 5.7 建议学习顺序

最后给出编号的学习顺序表，排序规则：

1. **依赖优先**：B 依赖 A，则 A 排在 B 前，并注明依赖关系。
2. **同层内按优先级**：Critical → High → Medium。
3. **快速见效**：耗时可忽略（约 5h）且能提振信心的 Medium 项可提前。
4. **领域知识靠后**：领域中／软技能差距适合与实践项目并行，不排在最前。

| # | 主题 | 类型 | 预估耗时 | 备注 |
|---|------|------|----------|------|
| 1 | 应急响应流程 | Hard | ~25h | 是第 3 步云上应急的前置 |
| 2 | CI/CD 与安全左移 | Tooling | ~10h | |
| 3 | 云平台安全（进阶） | Hard | ~25h | 依赖第 1 步 |
| 4 | AI 安全领域知识 | Domain | ~15h | 与真实项目并行 |

**预估总耗时：~75h**

### 5.8 保存报告

- 汇总模式：`gap-plans/report-YYYY-MM-DD.md`
- 定向模式：`gap-plans/report-YYYY-MM-DD-<公司slug>-<岗位slug>.md`（小写、空格转连字符、去特殊字符）

报告结构：标题与模式 → 「较上次报告的变化」（仅汇总模式且存在上一份报告时：已补齐的差距 / 新增差距）→ 差距热力图 → 学习计划 → 建议学习顺序。

保存后告知用户报告路径与用途。

## 六、硬性规则

1. **绝不编造职位**：只呈现真实检索结果或原始职位页中存在的岗位，不虚构公司、岗位、截止日期或薪资。
2. **严格去重**：呈现前必须同时检查 `seen_jobs.json` 与 `job_search_tracker.csv`；`ranked`、`expired` 条目也按已见过处理。
3. **搜索命中只是线索**：扫描器或搜索结果的标题／摘要只用于预筛，关键硬性要求必须抓取原始职位页确认。
4. **只收录未过期岗位**：跳过已过期、已关闭或截止日期已过的岗位。
5. **注意地理范围**：超出可接受通勤／搬迁范围且无强理由的岗位不收录。
6. **薪资只做区间参考**：以平台标注区间为准，不换算成确定承诺，不替用户承诺薪资。
7. **控制抓取量**：只对有潜力的命中做详情抓取；保持低频、低并发，遇到限流或风控迹象时降频或转人工确认，不做高频抓取或批量请求。
8. **不编造学习资源**：只引用真实检索到的资源，不虚构课程名、链接或作者；检索式带当前年份。
9. **差距判定要宽松**：能力矩阵中以任何形式出现过的技能都不算差距，避免误报。
10. **必存文件**：即使已在对话中给出结论，`seen_jobs.json`、台账与差距报告仍要落盘。
11. **状态字段不可丢**：重写 `seen_jobs.json` 条目时保留已有字段（含 `rank_score`／`rank_verdict`／`rank_date`）。
12. **写操作可回滚**：台账与状态文件的修改限定在本人求职记录内，不做破坏性覆盖；合并重复行前先确认。
